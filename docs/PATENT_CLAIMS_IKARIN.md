# Patent Application Materials: Technical Solutions, Architecture, and Algorithms (Contributions by I. Karin)

## 1. Field of the Invention and Utility
The invention relates to the field of distributed computing systems, cryptographic data protection, and interaction protocols for autonomous software agents based on artificial intelligence (LLM/AI Multi-Agent Systems). The invention is designed to provide legally binding non-repudiation, resilience against node collusion, and automated proof of execution correctness for financial and operational transactions.

---

## 2. Architectural Elements of the System

### 2.1. Distributed Heterogeneous Multi-Node Topology (Bank-A / Bank-B Architecture)
* **Sovereign Node Separation**: The system is built upon independent network nodes — an initiator node (**Bank-A / Purchaser Node**) and an executor node (**Bank-B / Vendor Node**). Each node operates within an isolated address space with its own proxy gateway (`ProxyAGateway`, `ProxyBGateway`), local database, and isolated cryptographic keystore.
* **Dedicated Asynchronous Notary Service (Merkle-Anchor Microservice)**: An architecturally isolated service for batch aggregation of cryptographic proofs, binding the local relational transaction journal to a public Layer 2 blockchain (L2 / Base Sepolia).

### 2.2. Architectural Interceptor Gateway for Autonomous Agent Cognitive Cycles (Cognitive Interceptor & Thought Stream)
* **Integration with Real Autonomous Reasoning Environment**: Binding the agent execution environment (Strands/AO Framework) with the cryptographic action commitment protocol.
* **Reasoning Interceptor Gateway (`POST /thought`)**: Interception of intermediate reasoning steps (*Reasoning Loop: Perception $\rightarrow$ Analysis $\rightarrow$ Action $\rightarrow$ Validation*) and `log_thought` tool invocations, enabling the association of the agent's internal rationale and motivation with a specific cryptographic envelope prior to executing a network call.

### 2.3. Dual-Layer Data Synchronization Pipeline (Hybrid Streaming & SQLite WAL Ledger)
* **Dual-Write Architecture**: Separation of event processing into persistent recording in a relational database journal using Write-Ahead Logging mode (`PRAGMA journal_mode = WAL;` with parameter `busy_timeout = 5000ms`) and concurrent broadcast streaming to clients via Server-Sent Events (SSE).
* **Defensive Stream Boundary**: An isolating layer on the client interface side that provides fault-tolerant parsing and sanitization of unstructured or malformed text blocks generated by LLM agents.

### 2.4. Anti-Collusion Participant Architecture (Witness & Escrow Topology)
* **Independent Co-signing Witness**: Introduction of an independent third party (`trust-agent-cloud` service) participating in transaction validation between the Acceptance phase and the Execution phase to prevent historical record falsification in the event of collusion between both interacting banks.
* **Split-Storage Model with Regulatory Escrow**: Distributed storage of encrypted proofs with the capability of decryption by an authorized supervisory authority without disclosing master keys to the witness.

## 3. Specific Technical Solutions and Algorithms

### 3.1. Bilateral Cryptographic Finalization Algorithm (D1 Dual-Signing Invariant)
* **Essence of the Solution**: Ensuring mutual non-repudiation of the operation execution result.
* **Execution Order**:
  1. The executor node (Proxy B) completes the tool operation, generates `ExecutionEnvelope`, signs it with its Ed25519 private key, and transmits it to the initiator node (Proxy A).
  2. Proxy A validates Proxy B's signature and verifies the output hash (`output_hash`).
  3. Proxy A applies a countersignature to `ExecutionEnvelope`.
  4. The transaction is considered finalized exclusively upon the presence of both cryptographic signatures.

### 3.2. Sequential Hash-Chain Engine (Append-Only Hash-Chain Engine)
* **Essence of the Solution**: Protecting the local transaction ledger against deletion, suppression, or reordering of records by a database administrator.
* **Mathematical Model**:
  Each $i$-th entry in the envelope table is assigned a strictly monotonic sequence number $\text{seq}_i$, and its hash is computed by the formula:
  $$\text{row\_hash}_i = \text{SHA-256}\Big(\text{JCS}\big(\text{seq}_i \parallel \text{prev\_hash}_i \parallel \text{envelope\_payload}_i\big)\Big)$$
  where $\text{prev\_hash}_i = \text{row\_hash}_{i-1}$, and for the initial entry $\text{prev\_hash}_0 = \text{GENESIS\_HASH}$.
* **Technical Result**: Any omitted record violates sequence monotonicity (`seq`), and any modification or deletion of a record breaks the hash chain for all subsequent entries.

### 3.3. Content-Addressable WORM Storage with Envelope Encryption (WORM Envelope-Encryption Engine)
* **Essence of the Solution**: Ensuring data availability and confidentiality of raw transaction data (`args`, `outputData`).
* **Execution Order**:
  1. Generation of a unique symmetric Data Encryption Key $\text{DEK} \in \{0, 1\}^{256}$ (AES-256-GCM algorithm).
  2. Encryption of the payload plaintext using the DEK key.
  3. Derivation of the block identifier: $\text{Blob ID} = \text{SHA-256}(\text{plaintext})$, strictly matching the commitment included in the envelope (`args_hash` / `output_hash`).
  4. Asymmetric key wrapping of the DEK under the public keys of the exchange participants and a designated regulator escrow key (Regulator Escrow).
  5. Storage of the encrypted blob in WORM (Write-Once-Read-Many) mode: an insertion with an existing ID and identical hash is ignored (idempotent), while an insertion with the same ID but conflicting content is blocked.

### 3.4. Secure Key-Transparency Registry Algorithm (Key-Transparency Registry)
* **Essence of the Solution**: Protection against retrospective repudiation of one's own signature (Key Repudiation).
* **Execution Order**:
  - Each public key rotation operation for a DID identifier must contain a digital signature from the prior active key (`prior_key_endorsement`).
  - A key revocation operation closes the validity time interval ($\text{valid\_from} \dots \text{valid\_until}$) without removing historical records from the registry.

### 3.5. Batched Merkle Notary Algorithm (Batched Merkle Notary Algorithm)
* **Essence of the Solution**: Cost-effective batch anchoring of multiple transactions into a blockchain while maintaining the ability to produce individual inclusion proofs.
* **Execution Order**:
  1. Accumulation of `trace_id` identifiers and envelope hashes in a `Pending Set` buffer.
  2. Construction of a balanced binary Merkle tree compliant with RFC 8785 (JCS).
  3. Computation of the inclusion path for each transaction (`inclusionProofs`: ordered list of sibling hash pairs and position indices).
  4. Transmission of the Merkle Root to a smart contract on the Base Sepolia network with generation of a canonical confirmation URI.

### 3.6. Dispute Pack Generation and End-to-End Verification Engine (`Dispute Pack Engine`)
* **Essence of the Solution**: Generation of a self-contained, indivisible evidence bundle suitable for independent audit and legal dispute resolution.
* **Bundle Structure**: Comprises the causal chain of three envelopes (`[INTENT] \rightarrow [ACCEPTANCE] \rightarrow [EXECUTION]`), participants' public keys, digital signatures, Merkle tree inclusion proof, and blockchain transaction receipt.
* **Verification Algorithm (Causal Verification)**:
  $$\text{intent\_hash} \equiv \text{AcceptanceReceipt.intent\_hash} \equiv \text{ExecutionEnvelope.intent\_hash}$$
  followed by signature verification and verification of the Merkle Path against the root anchored in the blockchain.

### 3.7. Governed Degraded-Mode Discipline (Degraded-Mode Discipline)
* **Essence of the Solution**: Preserving payment pipeline operational continuity during external witness outages while mitigating risk exposure.
* **Execution Order**:
  1. Upon unavailability of the co-signing service, limits are enforced: transaction value must not exceed `value_cap`, and operation rate in a sliding window must not exceed `rate_cap`.
  2. The transaction executes with an explicit `DEGRADED` status designation.
  3. A maximum reconciliation deadline is established (`reconciliation_deadline`).
  4. Once connectivity is restored, an asynchronous reconciliation procedure is triggered (`POST /reconcile/:traceId`) to obtain a retrospective witness signature.

## 4. Cross-Component Linkages and Interoperability Mechanisms

1. **Self-Healing Key Exchange Protocol (Key Auto-Retry Handshake)**: Mechanism for automatic detection of peer node state resets with initialization of key re-registration without disrupting active agent sessions.
2. **End-to-End Trace Identifier Normalization (URN UUID)**: Mechanism ensuring end-to-end correlation across LLM reasoning logs, SSE events, SQLite WAL transactions, Merkle tree nodes, and blockchain transactions via a unified `trace_id` identifier of format `urn:uuid:...`.
3. **Client-Side Local Cryptographic Verification Module (In-Browser Provenance Verifier)**: Drag-and-drop file verification mechanism in the browser computing SHA-256 via the Web Crypto API and matching against the blockchain hash without sending data to a server.

## 5. Patent Claims (Claim Set for Patent Applications)

1. **A method for ensuring non-repudiation and integrity of autonomous agent actions**, comprising partitioning a system into independent nodes, intercepting cognitive reasoning of an agent via a specialized API gateway, concurrently committing intents to a persistent database in WAL mode and broadcasting to an SSE stream, bilaterally signing an execution envelope by both interacting parties, and binding transaction ledger entries into a continuous append-only hash chain.
2. **The method of claim 1**, wherein the transaction payload is encrypted with an ephemeral symmetric key (DEK) and stored in content-addressable storage with an identifier $\text{Blob ID} = \text{SHA-256}(\text{plaintext})$, wherein the DEK is asymmetrically wrapped for participants and an independent regulatory escrow.
3. **The method of claim 1**, wherein upon failure of an external witness, the system transitions to a degraded mode with limits on operation value and rate, sets a reconciliation deadline, and performs automated retroactive countersigning after connectivity is restored.
